# Development

How to run, test, configure and deploy the lab. What the system is and how it works:
[`architecture.md`](architecture.md). Binding decisions: [`decisions.md`](decisions.md).

## Requirements

- Go (version in `server/go.mod`)
- Python 3.10+ (robot script, simulator, tests)
- Node.js 20.19+ (Nx, team page)

```bash
npm install
```

## Quick start (no hardware needed)

Start the server and the team page dev server with hot reload:

```bash
npm run dev
```

In a second terminal, start three simulated robots in the labyrinth:

```bash
npx nx run sim:run --robots=3 --world=sim/worlds/labyrinth.json
```

1. Control room: http://localhost:5173/admin, password `dev`. It shows the lab code `DEV1`.
2. Found a team: http://localhost:5173/join with code `DEV1` and a team name. The page then leads
   to the team page `/t/<token>`.
3. In the control room, drag robots onto the team (or pick them from the list).
4. In the control room, create a task (or import one from `docs/lab/aufgaben/`), publish it and
   assign it to the team. The team accepts it on its page; only then can it deploy and start runs.

Port 5173 is the Vite dev server with hot reload; http://127.0.0.1:8080 serves the embedded build
as on the VM. The local config runs every team on a scripted test model (`kind: fake`), so no API
key is needed; see [Models and API keys](#models-and-api-keys) for a real one.

## Tasks

Tasks run through [Nx](https://nx.dev). The workspace has four projects: `server`, `web`, `robot`
and `sim`. Server builds depend on `web:build`, so the binary always embeds the current team page.
Results of `lint`, `test` and the builds are cached, and `npx nx affected -t test` only tests what
changed compared to `main`.

| Command | What it does |
| --- | --- |
| `npm run dev` | `server:dev` and `web:dev` together |
| `npx nx run server:dev` | server with `deploy/local/lab.yaml` and dev secrets (HTTP 127.0.0.1:8080, MQTT :1883) |
| `npx nx run web:dev` | team page with hot reload on :5173, API calls go to the Go server |
| `npx nx run sim:run [--robots=2] [--world=…] [--delay-ms=150]` | simulated robots against the local server |
| `npx nx run-many -t lint test` | gofmt, go vet, TypeScript, Go tests, web tests, robot and simulator tests |
| `npx nx run sim:e2e` | smoke test: built server + one simulated robot + scripted model, no API key |
| `npx nx run web:e2e` | browser tests (Playwright, Chromium) against the same lab; screenshots in `web/e2e/screenshots/` |
| `npx nx run sim:grid` | regenerate the line field world and its build plan after changing `sim/grid.py` |
| `npx nx run robot:bundle [--config=robot/config.py]` | build `robot/dist/main.py` |
| `npx nx run robot:upload --config=robot/config.py [--port=…]` | bundle and upload to a CyberPi on USB (macOS) |
| `npx nx run server:build` / `server:build-linux` | build the server into `bin/` |
| `HOST=user@vm npx nx run server:deploy` | build for linux/amd64, copy to the VM, restart |
| `npx nx graph` | show projects and task dependencies |

Run `go test -race ./...` in `server/` before touching `agent`, `robots` or `tools`: they are
concurrent.

## Simulator

`sim/` runs the real bundled robot script under CPython with fakes for the vendor modules and a 2D
world. It talks real MQTT to the server, so everything above the robot behaves as in the lab.

- **Sensor noise** is on by default: ultrasonic dropouts and ghost echoes, color flicker at edges,
  gyro spikes, RGB noise and a color cast per robot. `--no-noise` gives ideal sensors.
- **Guest Wi-Fi:** `--delay-ms=150` delays every packet in both directions, so nothing works in the
  simulator that would come too late on a real robot.
- **Worlds** in `sim/worlds/`: `arena`, `labyrinth`, `labyrinth_rechts` (solvable by turning right
  at every wall), `labyrinth_gestoert` (the same with a box in the way), `linie` (line course),
  `gitter` (line grid with colored stripes, generated by `sim/grid.py`; never edit by hand).
- **Geometry** of the robot is assumed in `sim/mbot2.json` until measured.

## Models and API keys

The server talks to any OpenAI-compatible endpoint (Mistral, Ollama, …) or to Claude
(`kind: anthropic`, official Anthropic Go SDK), with retries, a fallback provider and a cost
estimate from the configured prices. `kind: fake` is a scripted test model that explores with the
real tools and needs no API key; `deploy/local/lab.yaml` uses it by default.

- Set `default: mistral` and `MISTRAL_API_KEY`, or `default: claude` and `ANTHROPIC_API_KEY`, for a
  real model. Only the `default` and `fallback` providers need their key; the server leaves out any
  other provider whose key variable is not set and logs it at startup.
- Locally, put the keys into `server/.env.local` (dotenv format, `export` allowed, git-ignored).
  Nx loads it for every `server` task, and Claude Code copies it into new worktrees
  (`.worktreeinclude`). Config files only name environment variables (`*_env`), never secrets.
- Teams run on `default` unless they choose another provider the control room released; the
  fallback applies to every team.
- **Claude:** the key comes from a Claude Console organization. Claude Max, Ultra and Team plans
  include monthly API credits for such an organization (claim them on claude.ai under Settings →
  Billing); the subscription login itself is not an API credential. The example configs use
  Claude Haiku 5.5, the cheapest model; switch `model` to `claude-sonnet-5-5` or `claude-opus-5-5`
  for harder tasks. If a request is declined, the client moves on to the configured fallback.

Every key of the configuration is documented in `configs/lab.example.yaml`.

## Real robots

1. Copy `robot/config_example.py` to `robot/config.py` and fill in robot ID, Wi-Fi (2.4 GHz) and
   broker credentials. `config.py` is git-ignored.
2. Connect the CyberPi with a USB data cable (a charge-only cable does not work), switch the
   battery on (on USB power alone the CyberPi does not answer) and close mBlock (it holds the
   port). Then bundle with the config inlined and upload:

   ```bash
   npx nx run robot:upload --config=robot/config.py
   ```

   It finds the CyberPi when exactly one `/dev/cu.usbserial-*` or `/dev/cu.wchusbserial*` exists;
   otherwise it lists the ports and you pass one with `--port=/dev/cu.…`. It waits 3 s for the
   CyberPi to boot, uploads to the firmware's staging slot (an interrupted upload keeps the old
   program), restarts the CyberPi and prints its output while uploading. macOS only.

   mBlock still works: `npx nx run robot:bundle --config=robot/config.py`, then upload
   `robot/dist/main.py` in upload mode.

On a new robot or firmware, first upload `robot/tools/hwcheck.py` alone (wheels in the air):

```bash
cd server && go run ./cmd/robotupload ../robot/tools/hwcheck.py
```

It tries every vendor call the script uses and prints `HW OK …` or `HW ERR …` per call to the
display and the serial log. All vendor API calls live in `robot/src/hw.py` and are marked `VERIFY`
until checked on hardware; values still to measure are in [`measurements.md`](measurements.md).
Limits of the stock firmware (script size, module loading): [`cyberpi-firmware.md`](cyberpi-firmware.md).

## Deploying

The server runs on an Azure VM; robots connect from the guest Wi-Fi via MQTT over TLS, lab PCs only
need HTTPS. Setup steps: [`deploy/azure/README.md`](../deploy/azure/README.md). Updates:

```bash
HOST=user@vm npx nx run server:deploy
```

| `configs/` | example lab configuration |
| `deploy/` | Azure VM, systemd unit, local development config |

## Conventions

- Decisions in [`decisions.md`](decisions.md) are binding; propose a deviation before
  implementing it.
- Long-term docs describe the current state in English. A PR that changes behaviour updates them
  in the same PR. [`protocol.md`](protocol.md) is the source of truth for MQTT; its example
  messages in `docs/examples/protocol/` are read by the Go and Python tests.
- Lab material and student-facing UI text are German; task files exist in German and English.
- The robot script stays MicroPython-compatible and never blocks while a motor runs.

Agent-specific working notes: [`CLAUDE.md`](../CLAUDE.md).
